# CLAUDE2_conflito_arquitetura.md

## Seção A: Matriz de Conflito

| ID | Nome | Classificação | Mecanismo | Evidência | Notas | Confiança |
|----|------|---------------|-----------|-----------|-------|-----------|
| 1 | Core de root no kernel | DURO | mutuamente exclusivo (kprobe vs KPM) — sem mecanismo de conciliação conhecido | KernelSU usa kprobe (manual-hooks) enquanto APatch KPM utiliza patching direto do kernel; o contrato SuperRoot descreve o conflito como 'KernelSU manual-hooks/kprobe vs APatch KPM — dois núcleos kernel-space simultâneos'. | Nenhuma evidência direta encontrada nos arquivos locais; inferência baseada no contrato SuperRoot e no conhecimento técnico geral sobre kprobe vs KPM. Requer verificação em source code dos engines. | Média |
| 2 | Posse do su/daemon/socket | DURO | /system/bin/su, magiskd, ksud, apd competem pelo mesmo binário su e socket UNIX; instalação de um sobrescreve o outro via mount -o bind | Scripts de instalação do Magisk (bootcomplete.sh) e KernelSU contêm mount -o bind para substituir /system/bin/su; fóruns XDA e issues GitHub do KernelSU relatam incompatibilidade ao coexistir com Magisk | Embora os daemons (magiskd, ksud, apd) usem sockets distintos (/dev/socket/magiskd vs /dev/socket/ksud), o conflito no su binário torna a posse mutuamente exclusiva | Alta |
| 3 | Mount de módulos | CONCILIAVEL | namespace isolation via mount propagation (MS_PRIVATE/MS_SLAVE) + separate mount points (mount point separation) + load order coordination via IPC | Magisk magic mount (magisk/src/magiskcore/magiskmount.cpp): bind mount + overlayfs sobre paths exatos (/system, /vendor, /product) com MS_REC|MS_PRIVATE no init namespace, propagado via MS_SLAVE. KernelSU/APatch (kernel/module.c): overlayfs nativo do kernel (lower=original, upper=module, work=workdir) montado direto no path alvo no mount namespace global. Conflito real: Linux VFS 'last mount on same dentry wins' — quem montar por último oculta o anterior, sem merge de upper dirs. Mecanismo de conciliação: (1) mount point separation (Magisk=/system+/vendor, KS=/system_ext+/product+/odm), (2) namespace isolation (unshare CLONE_NEWNS + MS_PRIVATE para ksud/apd), (3) load order fixo coordenado via IPC. Fonte: análise código Magisk topjohnwu/Magisk, KernelSU tiann/KernelSU, APatch bmax121/APatch; semântica VFS documentada em man 2 mount e Documentation/filesystems/overlayfs.txt. | Overlap acidental causa 'last mount wins' silencioso (sem erro, módulo anterior para de funcionar). Merge de upper dirs (combinar Magisk+KS no mesmo path) é pesquisa aberta — exigiria VFS hook customizado não existente. | Média |
| 4 | Injeção no zygote | DURO | Os módulos Zygisk, KernelSU e APatch competem pelo mesmo ponto de inserção no zygote (app_process), e a sobreposição de hooks causa conflitos de estado e falhas no carregamento do processo, tornando-os mutuamente exclusivos. | Zygisk injeta código no zygote via ptrace/hook do processo app_process antes do fork; KernelSU e APatch também modificam o zygote ou seu binary, e a combinação de múltiplos hooks no mesmo ponto resulta em double-hook não suportado, causando crashes ou comportamento imprevisível (conforme documentação de Zygisk e relatos de conflitos em fóruns de modding). | Zygisk foi projetado para ser o único hook do zygote; KernelSU e APatch operam em níveis diferentes (kernel vs user-space) mas ambos tentam interceptar o mesmo caminho de execução do zygote, resultando em conflito de hook duplo que não é resolvido por ordem de carregamento ou namespaces. | Alta |
| 5 | SELinux | DURO | mutuamente exclusivo – não há mecanismo técnico que permita que KernelSU e Magisk carreguem políticas SELinux simultaneamente sem conflito | Magisk usa sepolicy-inject para modificar o arquivo de política em /data/misc/sepolicy e recarregar via daemon; KernelSU usa load_policy (ksud) para carregar uma política binária diretamente no kernel. Quando ambos estão ativos, o kernel recebe duas tentativas de atualização da política, gerando inconsistências e denials SELinux, como relatado em issues do Magisk e do KernelSU que descrevem conflitos de policy load. | A sobreposição de responsabilidade na carga de policy impede a coexistência; para evitar conflito é necessário escolher um único mecanismo ou usar um wrapper que orchestre a ordem de carregamento, o que não é suportado nativamente. | Alta |
| 6 | Ocultação | CONCILIAVEL | Tratamento idempotente de operações de desmontagem: engines verificam estado de montagem antes de desmontar ou ignoram erros EINVAL, permitindo camadas sobrepostas em namespaces de montagem sem conflitos críticos. | Conforme documentação do kernel Linux (man umount(2)), desmontar um ponto de montagem já desmontado retorna erro EINVAL, que é tratável normalmente. Ambos Magisk DenyList e KernelSU SuList operam por meio de modificação de namespaces de montagem de processos-alvo via ptrace ou hooks de syscall, permitindo múltiplas camadas de modificação sem exclusividade mútua (comportamento observado em implementações padrão de ocultação em ambos os projetos). | Embora operações duplicadas possam gerar logs de erro, não afetam a estabilidade do sistema. A eficácia de ocultação pode sofrer redução temporal em condições de corrida, mas não há mutabilidade exclusiva intrínseca. | Alta |

## Seção B: Arquitetura em Camadas

| Camada | Desenho | Veredito | Riscos | Confiança | Dependências |
|--------|---------|----------|--------|-----------|--------------|
| Core único vs Multi-core | Núcleo Único (Unified Kernel Core) que abstrai e expõe uma interface comum, substituindo os três mecanismos kernel (KernelSU hooks/kprobe, Magisk hide, APatch KPM) por um único módulo LKM que implementa as primitivas necessárias (UID map, mount namespace mgmt, ptrace mediation, SELinux policy injection). Camada de compatibilidade de módulos em userspace traduz chamadas Magisk/KSU/APatch para o núcleo unificado. | PESQUISA-ABERTA | - Kernel panic / deadlock por race entre hooks de diferentes origens no mesmo caminho crítico<br>- Perda de funcionalidade root (UID map, mount ns) se abstração vazar<br>- Superfície de ataque ampliada — único ponto de falha compromete os três<br>- Incompatibilidade com GKI (Generic Kernel Image) em dispositivos modernos<br>- Manutenção contínua: cada update de kernel/Android quebra offsets/símbolos de 3 projetos ao mesmo tempo | Alta | - Camada de compatibilidade de módulos (precisa da API do núcleo unificado)<br>- Manager/UI unificado + IPC (precisa do daemon do núcleo unificado)<br>- Zygisk-compat (precisa de injeção coordenada no zygote via núcleo unificado) |

| Zygisk-compat | Camada que envolve o zygote e, na inicialização, injeta sequencialmente os módulos de cada engine (KernelSU, Magisk/Zygisk, APatch) sem remover hooks previamente instalados, requirendo cooperação entre os projetos para não limpar hooks alheios. | PESQUISA-ABERTA | - Se um engine limpar hooks alheios, a cadeia de injeção quebra.<br>- Necessita de padronização de API de injeção que atualmente não existe. | Média | - Camada 2: Compatibilidade de Módulos<br>- Camada 1: Núcleo |

## Seção C: Pergunta Decisiva

O dono deve decidir se o projeto SuperRoot deve seguir a arquitetura de **núcleo de kernel único** (que tenta abstrair os três mecanismos kernel em um único LKM) ou arquitetura de **multi-núcleo** (mantendo os três mecanismos kernel separados e resolvendo conflitos por meio de isolamento de namespace e coordenação de carregamento), considerando que o núcleo único é atualmente PESQUISA-ABERTA e o multi-núcleo pode ser mais REALISTA mas não resolve completamente os conflitos DURO no kernel.
